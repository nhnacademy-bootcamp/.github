## 팀 프로젝트

- 각 팀은 별도의 Organization을 만들어 프로젝트를 진행하며, 게이트웨이/인증/도메인별 API 서버를 repository 단위로 분리하는 **MSA 구조**로 설계했습니다.

- 스크럼·회의록·위키 등 문서화 repository를 함께 운영하며 실무형 협업 프로세스를 경험했고, 일부 팀은 자체 도메인을 통해 서비스를 배포했습니다. (e2bs.shop, bluebooktle.shop, trillion-book.shop, javame.live 등)

#### BE 1기

##### on-7 (MarketGG)

**Market GG**는 책이 아닌 **밀키트**를 파는 쇼핑몰로, 구독형 멤버십 **GG 패스**를 상품 판매와 함께 묶었습니다. 검색창에 한글을 영문 자판으로 잘못 쳐도 상품을 찾아 주는 Elasticsearch 검색, 스케일 아웃을 염두에 두고 로컬과 Object Storage를 바꿔 끼울 수 있게 만든 파일 저장 구조 등 기술 고민을 README에 Technical Issue로 정리해 두었습니다.

- Repository 주소: https://github.com/on-7
- 프로젝트 특징:
  - **오타·자동완성까지 다룬 검색** — 상품과 고객센터 게시글에 영/한 오타 변환, 동의어·연관어, 자동완성, 카테고리 내 가격별 검색을 적용하고, 자체 트랜잭션이 없는 Elasticsearch는 Logstash 주기 동기화로 MySQL과 정합성을 맞추며 X-Pack으로 보안 활성화
  - **저장소를 갈아 끼우는 파일 관리** — 빈을 동적으로 주입해 로컬 디스크와 NHN Cloud Object Storage 중 하나를 골라 쓰도록 설계해 기존 코드 변경 없이 클라우드로 이전, TOAST UI Editor hook으로 이미지를 먼저 올리고 본문에는 URL만 저장
  - **이벤트로 움직이는 쿠폰 지급** — 회원가입·베스트 후기 선정은 Spring Event, 생일 쿠폰은 Scheduler, 매월 1일 등급 갱신과 등급별 쿠폰은 Batch + Scheduler로 나누어 자동 지급
  - **서명 검증을 더한 설정 서버** — 외부 저장소로 분리한 Spring Cloud Config에 **ECDSA** 서명을 적용하고, Nginx에서 서브도메인 분기와 버전 정보 숨김 처리
  - **GG 패스와 고객센터** — 구독 신청·해지·갱신일 확인, 공지사항·1:1 문의·FAQ 세 게시판을 하나의 서비스 메서드로 통합 처리하고 `@RoleCheck`로 막지 못하는 권한은 서비스 계층에서 검사

##### Gaship

**Gaship**은 가구를 팔고 배송·설치까지 관리하는 쇼핑몰입니다. 지역별 배송 가능 여부와 하루 물량, 설치 기사 일정처럼 무겁고 부피 큰 상품에서만 생기는 운영 문제를 데이터 모델로 옮겨, 같은 기수의 서점 프로젝트들과 전혀 다른 기능 구성을 갖췄습니다.

- Repository 주소: https://github.com/Gaship
- 프로젝트 특징:
  - **배송·설치 운영 모델링** — 상위 지역에서 하위 지역으로 내려가는 지역 주소 조회와 배달 가능 여부, 지역별 최대 물량, 직원 관리, 날짜별 **수리·설치 스케줄**을 각각 독립 도메인으로 구현
  - **취향 태그로 고르는 추천** — 회원이 고른 태그와 상품 태그를 연결하고 상품평·주문 상세 데이터를 함께 써서 회원마다 다른 상품을 추천
  - **초성·자판 오타 검색** — Elasticsearch 분석기로 `rkrn`(가구), 초성 `ㄱㄱ`, 동의어 검색을 지원하고 ES 저장은 DB 트랜잭션과 분리
  - **개인정보 이중 암호화** — 회원 개인정보는 **AES-256**으로 암호화 저장, 로그인 시에는 **SHA-512**로 질의하고 AOP로 쇼핑몰 서버 접근 권한을 확인
  - **라인 커버리지 83.7%** — 쇼핑몰 서버의 목표치 80%를 넘긴 결과를 공개하고, 체크스타일·SonarLint·SonarQube가 지적한 약점을 팀 공통 과제로 개선

#### BE 2기

##### NHN-BookPub

**BookPub**은 선착순 쿠폰처럼 트래픽이 한순간에 몰리는 상황을 **RabbitMQ** 전용 서버로 받아내고, 자주 보는 화면은 Spring Cache와 Redis로 쿼리 수를 줄이는 데 공을 들였습니다. 배송은 더미 서버와 배치를 엮어 '배송준비 → 중간 허브 경유 → 도착 → 구매확정'까지 주문 상태가 시간에 따라 실제처럼 흘러가도록 만들었습니다.

- Repository 주소: https://github.com/NHN-BookPub
- 프로젝트 특징:
  - **메시지 큐로 받는 선착순 쿠폰** — 선착순 지급 요청은 RabbitMQ로 처리하고 이달의 쿠폰 수량은 Redis로 체크, 회원 권한에 따라 등급별 쿠폰 지급 가능 여부를 판단

##### nhnacademy-aiot1-Smoothing (Smoothing)

Smoothing은 24시간 전력 수요 예측을 근거로 경부하 시간대에 에너지를 저장하는 가상 발전기를 돌리는 전력 관리 솔루션입니다. Broker 생성과 Topic 구독을 동적으로 처리하는 룰 엔진을 직접 만들었고, LoRa·MQTT 수집부터 월간 보고서까지 갖춰 자체 도메인 **smoothing.live**에 배포했습니다.

- Repository 주소: https://github.com/nhnacademy-aiot1-Smoothing
- 프로젝트 특징:
  - **수요 예측 기반 가상 발전기** — 하루 예측 전력과 실측 전력을 비교 조회하고, 예측값에 따라 가상 발전기가 자동 동작해 발전량과 발전기 로그를 기록
  - **직접 만든 룰 엔진** — JSON Parsing·Switch 노드로 규칙을 처리하고, 디바이스 서버 요청에 맞춰 Broker를 만들고 Topic을 구독하며 Broker 에러와 이상치를 RabbitMQ로 통보
  - **LoRa·MQTT 수집** — LoRa, Milesight, MQTT, Node-RED로 전력 데이터를 받아 InfluxDB에 저장하고 전압·누전을 조회
  - **실시간 요금 카운터와 목표 게이지** — 10분·1시간·1일 단위 전력 그래프, 실시간 전기 요금 카운터, 실시간 목표량 게이지와 연도별 목표 달성 여부 조회, 태그·기간별 비교 현황
  - **FCM·웹훅 알림과 월간 보고서** — 회원 승인 요청과 이상치 발생 시 FCM 푸시와 웹훅으로 알리고 한 달 주기로 보고서 생성
  - **JWT 상태 구분 검증** — 만료·조작·정상 토큰을 구분 검증하고 Redis Refresh Token 삭제, 이메일 인증, 회원 승인/거절과 출석 관리 제공

##### nhnacademy-aiot1-T1

**AIOTONE**은 워터펌프 같은 공장 모터에 연결된 ADC 장비에서 신호를 직접 받아 머신러닝으로 모터 이상을 감지하는 시스템입니다. 상용 수집 도구를 그대로 쓰지 않고 ADC 게이트웨이, Telegraf 역할의 수집기, R 전처리 서버를 팀이 직접 만들어 하드웨어부터 이상 탐지까지 이어지는 경로를 구현했습니다.

- Repository 주소: https://github.com/nhnacademy-aiot1-T1
- 프로젝트 특징:
  - **USB 연결을 감지하는 ADC 게이트웨이** — 센서 신호를 고속으로 수집해 `data/d/{도메인}/f/{공장}/g/{게이트웨이}/m/{모터}/c/{채널}` 계층의 MQTT 토픽으로 변환하며, USB 리스너로 장치 연결·해제를 감지하고 5분마다 기기의 수집 여부를 확인
  - **직접 만든 Telegraf 대체 수집기** — `simple-telegraf`가 MQTT 데이터를 타임스탬프에 맞게 잘라 고속 채널 수만큼 나눠 InfluxDB에 넣고, 연결 기기 상태는 주기적으로 RDB에 기록
  - **R 기반 전처리 파이프라인** — 스케줄링으로 InfluxDB에서 데이터를 가져와 `-Inf`/`Inf` 값과 결측치를 처리하고 정규화한 뒤 다시 InfluxDB에 저장하고, Python 머신러닝 서버가 이 데이터로 이상치를 탐지
  - **모터 가동률 대시보드** — 전체·가동 중·비정상 모터 수, 일·주·월별 가동률, 구역별 요약, 모터별 상태와 시간별 변화 추이를 제공
  - **이상 알림과 리포트 메일** — 이슈가 생기면 Dooray Hook 메시지를 보내고, ADMIN 사용자 전원에게 HTML 리포트 메일을 발송
  - **사내 Maven 저장소 운영** — 공통 라이브러리를 갱신하면 GitHub 기반 Maven 저장소에 자동 배포하고 Dooray로 알리며, Front 서버는 이중화로 운영

##### nhnacademy-aiot1-5

**아이오티타임(IOTEATIME)**은 사용자가 정한 한 달 전기 요금 예산을 기준으로, 이번 달 요금이 예산을 넘을지 미리 알려 주는 스마트 전력 관리 시스템입니다. Prophet 모델로 채널별 월 사용량을 예측하고 배치 작업으로 실제·예측 전기 요금을 계산해 예산 대비 현황을 보여 주며, 환경 센서를 근거로 UC300 장치를 제어해 전력을 조절합니다.

- Repository 주소: https://github.com/nhnacademy-aiot1-5
- 프로젝트 특징:
  - **교차 검증으로 튜닝한 Prophet 예측** — 주말·계절·추세 하이퍼파라미터를 교차 검증해 RMSE가 가장 작은 조합을 고르고, 사용량 변화가 없는 채널은 학습 없이 0으로 처리. 매일 0시 5분 이상치 기준 계산, 0시 10분 예측이 자동 실행
  - **Tasklet 배치 전기 요금 계산** — 일·월별 실제 사용량과 일별 예측치 각각에 대해 전기 요금을 계산해 누적 요금, 예측 요금, 요금 게이지 차트와 요금 추천 UI로 제공
  - **브리지 서버와 룰 체인** — 브리지 서버가 MQTT·Modbus 센서 데이터를 RabbitMQ로 발행하고, 룰 엔진이 큐의 데이터를 룰 체인에 통과시켜 Modbus 파싱, InfluxDB 저장, 이상치 감지와 Front·API·컨트롤 서버 전송을 처리
  - **원격 브리지 프로비저닝** — 룰 엔진이 브리지 프로퍼티를 만들어 외부 인스턴스에 scp로 보내고 스크립트를 실행해 새 브리지를 띄우며, Modbus 매핑 테이블을 갱신
  - **조직 단위 권한 제어** — `@AdminOnly` AOP와 조직 코드 검증 AOP로 접근을 제한하고, 권한별 사이드바와 datatables 기반 관리자 페이지에서 예산·조직·사용자를 관리

##### nhnacademy-aiot3-omagotchi (Omagotchi)

**Omagotchi**는 KDT 연수생의 출결과 공부 시간을 캐릭터 성장, 퀘스트, 랭킹으로 바꿔 주는 학습 관리 플랫폼으로, 실습실 온도·습도·CO2도 함께 관리합니다. 가상 데이터 18,000행으로 학습한 LightGBM 모델이 내일 공부 시간을 예측해 개인별 퀘스트 목표를 정하며, 기존 규칙보다 오차를 하루 93분 줄였습니다.

- Repository 주소: https://github.com/nhnacademy-aiot3-omagotchi
- 프로젝트 특징:
  - **검증 원칙을 지킨 공부 시간 예측** — 피처 32개로 학습한 LightGBM이 test MAE 83.5분을 기록해 기존 규칙(최근 7 등원일 평균) 대비 93.2분 개선. 시간 순서 분할과 사용자별 누수 방지를 적용하고 test는 한 번만 채점했으며, 요일 피처를 빼면 MAE가 48.9분 나빠지는 것을 제거 실험으로 확인
  - **예측이 실패해도 끊기지 않는 퀘스트** — 예측값은 3시간 30분~11시간 30분으로 제한하고, 예측에 실패하면 최근 등원 평균 규칙으로, 그마저 불가하면 기본값으로 단계적으로 폴백해 퀘스트 발급이 중단되지 않음
  - **도구를 호출하는 Spring AI 챗봇** — Gemini 기본 모델과 자체 호스팅 Ollama 폴백을 요청 단위로 전환하고, 공부 시간 요약·학습 패턴·공간 환경·기상청 날씨 등 Tool Calling 6종으로 직접 조회해 SSE로 스트리밍 응답

  - **운영급 배포·관측 인프라** — Cloudflare Tunnel→Nginx 진입, Commit SHA 태그 GHCR 이미지, A/B 롤링 배포와 실패 슬롯 복구, 배포 잠금 직렬화와 Kill Switch를 갖추고 Prometheus·Grafana·Tempo·ElastAlert2로 로그·메트릭·트레이스를 관측
  - **실행 특성 기준의 최소 MSA** — MQTT 상시 구독(Rule)과 Python ML 런타임(Prediction)처럼 실행 환경이 다른 영역만 분리하고, 결정 근거는 ADR로 문서화

##### nhnacademy-aiot3-insighton (InsightOn)

**InsightOn**은 여러 고객사가 데이터와 인프라를 완전히 분리한 채 함께 쓰는 B2B 스마트 오피스 SaaS로, LLM이 실내 통계와 날씨·미세먼지를 보고 공조 기기를 직접 제어할 수도 있게 설계했습니다. LLM이 만든 명령을 코드 규칙으로 한 번 더 검증하는 관문, Tool Calling 대화 복원 문제 해결, Kubernetes 위에서 MQTT 연결과 룰 엔진을 나눠 맡는 이중화 설계처럼 운영 안정성을 다룬 기술적 결정이 돋보입니다.

- Repository 주소: https://github.com/nhnacademy-aiot3-insighton
- 프로젝트 특징:
  - **LLM 명령 검증 관문** — 공간별로 `SUGGESTION`(제안 후 수락)과 `AI_DIRECT`(즉시 집행) 모드를 고르며, LLM이 만든 명령은 허용값·수치 범위 규칙을 검사하는 단일 관문을 통과해야 실제 기기로 전송. 챗봇 도구 역시 그룹·위치 경계를 LLM이 아닌 서버 코드가 강제
  - **Tool Calling 대화 복원 문제 해결** — 대화 이력에 텍스트만 저장하면 도구 호출 기록이 사라져 Gemini가 이상하게 반응하는 문제가 있어, 공식 Redis 스타터 대신 `toolCalls`·`toolResponses`까지 직렬화하는 `ChatMemoryRepository`를 직접 구현
  - **리포트 생성 병렬화와 호출 제한** — 주간·월간 LLM 진단 리포트를 가상 스레드로 공간별 병렬 처리하되, Gemini 분당 요청 제한에 맞춰 Semaphore로 동시 외부 호출을 10개로 묶고, 패턴이 여러 개여도 공간당 LLM 호출은 1회로 줄임
  - **Consistent Hash 기반 룰 엔진 이중화** — 노코드 DAG 플로우(SpEL 조건, 시간대·빈도 제한, 센서 간 AND)를 고정 2인스턴스 active-active로 운영하며, RabbitMQ Consistent Hash Exchange로 같은 `location_id`를 같은 인스턴스에 보내고 Redis Heartbeat로 상대 장애 시 파티션을 흡수
  - **StatefulSet 서수로 나누는 MQTT 연결** — Core Pod의 서수로 슬롯을 자동 주입해 ChirpStack(LoRaWAN) 게이트웨이 연결 소유권을 나누고, Redis 분산 락과 약 30초 유예 후 백업 인스턴스 인계로 장애에 대응
  - **ArgoCD GitOps 배포** — GHCR 이미지 SHA로 매니페스트 저장소를 갱신하면 ArgoCD가 Kubernetes 클러스터에 동기화하며, 서비스별 독립 PostgreSQL과 InfluxDB 장애가 수집 경로로 번지지 않는 Fail-Silent 구조
